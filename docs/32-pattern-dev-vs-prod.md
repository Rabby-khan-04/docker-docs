# 32 — Pattern: Dev vs Prod Setups

> Verified on: Docker Engine **29.8.2**, Compose **v5.6.0**, BuildKit **v0.33.1**, Ubuntu 26.04.1 LTS, x86_64.

## 1. Simple explanation (like I'm 7)

You want two different environments: **development** (fast, messy, with code reload, bind mounts, debug tools) and **production** (strict, boring, immutable, resource limits, no dev tools). You do not want the development config to leak into production by accident.

This chapter shows the standard pattern: one `compose.yaml` for production, one `compose.override.yaml` for development. They live in the same directory, and Compose merges them when you run `docker compose up`, but you can run them separately.

## 2. Real name

### The two-file pattern

| File | Purpose | Key differences |
| :--- | :--- | :--- |
| `compose.yaml` | **Production base.** Immutable image, no bind mounts, real resource limits, health checks, production `NODE_ENV`. | - No `volumes:` that mount host source code\n- `APP_ENV: production`\n- `deploy.resources.limits` (memory, cpu)\n- `restart: unless-stopped`\n- Healthcheck configured\n- No `command: --watch`\n\n| `compose.override.yaml` | **Development overrides.** Added on top of the base. Bind mounts, `--watch`, dev env vars, debug tools. | - `ports: "127.0.0.1:3080:3000"` (different host port)\n- `APP_ENV: development`\n- `command: ["node", "--watch", "server.js"]`\n- `volumes: - .:/app` (bind mount)\n- `volumes: - node_modules_keep:/app/node_modules`\n- `restart: unless-stopped` (same, but respected differently)\n\n### Running each setup

```console
# Development: include the override (auto-loaded)\n$ docker compose up\n# Runs both compose.yaml + compose.override.yaml\n\n# Production: use only the base file\n$ docker compose -f compose.yaml up\n# Runs only compose.yaml, ignoring the override\n\n# Dev mode with explicit override flag\n$ docker compose --profile dev up\n# (if using profiles)\n```

### Why the override file must NOT be in production

If `compose.override.yaml` exists in the directory and you run `docker compose up`:\n\n1. Compose auto-loads the override file.\n2. The override's `APP_ENV: development` overrides the base's `APP_ENV: production`.\n3. The override's `command: ["node", "--watch", "server.js"]` replaces the production `CMD`.\n4. The override's `volumes: - .:/app` bind-mounts the host source code into the container.\n\n**Result:** You are running development settings in production. This is a common accident.\n\n**Fix:** Always run `docker compose -f compose.yaml up` for production.\n\n### Variable precedence — why the override wins

The Compose merge logic follows this order (lowest to highest precedence):

1. **Base file** (`compose.yaml`) keys.\n2. **Override file** (`compose.override.yaml`) keys redefined.\n3. **`-.env` file** variables (if present).\n4. **`-e`** flags on the `docker compose up` command line.\n5. **Environment variables** from the host shell.\n\nSo if the override file has `APP_ENV: development` and the base has `APP_ENV: production`, the override\nwins. This is intentional for development, but dangerous in production.\n\n### UID/GID and permission considerations

When the override adds `volumes: - .:/app`, files created on the host are owned by the host user.\nIf the container runs as a different user (e.g., `node` with UID 1000), there can be permission\nissues.

| Situation | Fix |
| :--- | :--- |
| Host UID matches container UID (both 1000) | No fix needed — it just works. |
| Host UID differs from container UID | Use `chown -R 1000:1000 /app` inside the container, or adjust mount options. |
| Read-only mount (safer for production-adjacent dev) | ` -v .:/app:ro` — the mount is read-only, no writes back to host. Useful if you only need to read source, not write. |

### Comparing dev vs prod — a quick checklist

| Question | Development answer | Production answer |
| :--- | :--- | :--- |
| **Bind mounts?** | Yes, `-v .:/app` for code reload | No, image is immutable |
| **`APP_ENV`?** | `development` | `production` |
| **`command`?** | `node --watch server.js` | `node server.js` |
| **Resource limits?** | Usually none (or generous dev limits) | Real limits (`deploy.resources.limits.memory`, `--memory`) |
| **Dev tools?** | May be present (debuggers, etc.) | None (minimal image) |
| **Image rebuilds?** | Not needed during dev iteration | Required on every deploy |
| **Override file?** | Present (`compose.override.yaml`) | Must be absent or explicitly excluded (`-f compose.yaml`) |

When to use these patterns and when NOT to\n\n### Use dev vs prod setups when\n\n- **You want a development environment** that is fast and messy, and a production\n  environment that is strict and boring.\n- **You want to prevent config leakage** between dev and prod (override file not applied in prod).\n- **You want fast iteration** in dev (bind mounts + `--watch`) and reliable deploys in prod\n  (immutable image, resource limits).\n- **You are working in a team.** The base file is committed to git (production shape). The override\n  file is typically git-ignored (dev-only settings).\n\n### Do not use these patterns when\n\n- **You have a single-container app.** `docker run` is simpler.\n- **You do not understand the override file auto-loading.** If you do not want the override,\n  remove or rename the file, or use `-f compose.yaml`.\n- **You are running production with bind mounts.** Bind mounts in production are slower, less\n  secure, and can lead to unexpected behavior. Use immutable images instead.\n- **You do not distinguish between dev and prod config.** If your app is the same in both\n  environments, you may not need two files.\n\n### A practical dev vs prod pattern\n\nIf you follow everything in this chapter, your file structure looks like this:\n\n```text\ndocker-learn/\n├── compose.yaml          # production base, committed to git\n├── compose.override.yaml # development overrides, git-ignored\n├── Dockerfile            # multi-stage, production-ready\n├── package.json\n├── server.js\n├── .dockerignore\n└── ...\n```\n\n```yaml\n# compose.yaml — production base (committed to git)\nservices:\n  api:\n    build: .\n    restart: unless-stopped\n    ports:\n      - \"127.0.0.1:3000:3000\"\n    environment:\n      APP_ENV: production\n    healthcheck:\n      test: [\"CMD\", \"node\", \"-e\", \"fetch('http://127.0.0.1:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))]\n      interval: 10s\n      timeout: 3s\n      start_period: 5s\n      retries: 3\n    deploy:\n      resources:\n        limits:\n          memory: 256M\n          cpus: '0.5'\n```\n\n```yaml\n# compose.override.yaml — development overrides (git-ignored)\nservices:\n  api:\n    ports:\n      - \"127.0.0.1:3080:3000\"\n    environment:\n      APP_ENV: development\n    command: [\"node\", \"--watch\", \"server.js\"]\n    volumes:\n      - .:/app\n      - node_modules_keep:/app/node_modules\n\nvolumes:\n  node_modules_keep:\n```\n\n```console\n# Development: include the override (auto-loaded)\n$ docker compose up\n\n# Production: use only the base file\n$ docker compose -f compose.yaml up\n```\n\n## 5. Common mistakes\n\n**1. `docker compose up` in production with the override file present.**\n\n```console\n$ docker compose up\n# The override is auto-loaded!\n# APP_ENV: development (from override)\n# command: [\"node\", \"--watch\", \"server.js\"] (from override)\n# volumes: - .:/app (from override) — bind mount in production!\n```\n\n**Fix:** Run `docker compose -f compose.yaml up` for production.\n\n**2. Forgetting that the override file is auto-loaded.**\n\nIf you do not want the override, remove or rename the file, or use `-f compose.yaml` to\npoint to a different base file.\n\n**3. `APP_ENV: development` leaking into production.**\n\nThe override's `environment: APP_ENV: development` overrides the base's\n`APP_ENV: production`. This can cause development-specific behavior (verbose logging,\ndev webpack config, etc.) to run in production.\n\n**4. `node --watch server.js` running in production.**\n\nThe override's `command: ["node", "--watch", "server.js"]` replaces the production\n`CMD [\"node\", \"server.js\"]`. In production, the watcher is unnecessary and may cause\nunexpected restarts.\n\n**5. Bind mounts in production.**\n\nThe override's `volumes: - .:/app` bind-mounts the host source code into the production\ncontainer. This is slower, less secure, and may allow accidental writes to the host\nfilesystem. Production should use immutable images.\n\n**6. Not git-ignoring the override file.**\n\nIf `compose.override.yaml` is committed to git, every team member gets the dev settings.\nAdd it to `.gitignore`: `compose.override.yaml`\n\n**7. Assuming `docker compose -f compose.yaml up` removes the override permanently.**\n\nIt runs without the override for that command. The file is still there; running `docker compose up\n` (without `-f`) will reload it.\n\n**8. Confusing `compose.override.yaml` with `compose.fallback.yaml`.**\n

There is no `compose.fallback.yaml` in the Docker Compose spec. The only standard override\nfile name is `compose.override.yaml`.\n\n**8. Forgetting resource limits in development.**\n\nDevelopment may not need the same strict limits as production, but setting some minimal\nlimits (e.g., `--memory 512m`) is polite on a shared machine.\n\n**9. `docker compose up` showing unexpected services.**\n\nIf you see services you did not define, check if an override file is adding them, or if\nthere are hidden compose files in parent directories.\n\n**10. `docker compose config` showing merged config you did not expect.**\n\nThe merge logic follows precedence rules. The override file's keys win over the base.\nUse `docker compose -f compose.yaml config` to see only the base.\n\n---\n
