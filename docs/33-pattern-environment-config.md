# 33 — Pattern: Environment-Specific Config

> Verified on: Docker Engine **29.8.2**, Compose **v5.6.0**, BuildKit **v0.33.1**, Ubuntu 26.04.1 LTS, x86_64.

## 1. Simple explanation (like I'm 7)

You have one Docker image, but you want it to behave differently depending on where it runs: development, staging, or production. The image is the same, but the **configuration** is different — environment variables, database URLs, feature flags, etc.

This chapter shows how to use `.env` files, Compose variable interpolation, and `env_file` so you build the image once and promote it to any environment.

## 2. Real name

### The `.env` file

```env
# .env (in the compose project directory)\nAPP_ENV=development\nDB_HOST=db\nDB_PORT=5432\nNEXT_PUBLIC_APP_NAME=my-app\n```\n\n| Variable | Value | Used by |
| :--- | :--- | :--- |
| `APP_ENV` | `development` or `production` | The app reads this to change behavior. |
| `DB_HOST` | `db` | DNS name of the database service (set by Compose networking). |
| `DB_PORT` | `5432` | PostgreSQL port. |
| `NEXT_PUBLIC_APP_NAME` | `my-app` | Next.js app — available in the client bundle (safe to commit). |

### Variable interpolation in Compose

```yaml
# compose.yaml\nservices:\n  api:\n    environment:\n      - APP_ENV\n      - DB_HOST\n      - \"DB_PASSWORD=${DB_PASSWORD}\"\n```\n\nHere `APP_ENV` and `DB_HOST` are replaced by the values from the `.env` file. `DB_PASSWORD=${DB_PASSWORD}` is explicitly quoted and also interpolated.\n\n### `env_file` vs `environment`\n\n| Source | Syntax | Interpolation | Precedence |
| :--- | :--- | :--- | :--- |
| `environment:` | `KEY: VALUE` inline | Yes (`${VAR}`) | Lowest (overridden by `-e`) |
| `environment_file:` | Path to `.env` file | Yes (`${VAR}`) | Medium |
| `-e KEY=VALUE` | Command line | No (literal) | Highest |
| `.env` file | Same as `-e` but in a file | Yes (`${VAR}`) | Medium |
| `docker run -e` | Command line | No (literal) | Highest (outside compose) |

### Variable precedence (lowest to highest)\n\n1. **Default values** in the Dockerfile `ENV` instruction.\n2. **`environment:`** key in the service definition.\n3. **`environment_file:`** in the service definition.\n4. **`.env` file** in the compose project directory.\n5. **`-e`** flag on the `docker compose up` command line.\n6. **`-e`** flag on the `docker run` command line.\n\nLater sources **override** earlier ones. So `-e APP_ENV=production` after `.env: APP_ENV=dev` results in `APP_ENV=production`.

### Real-world `.env` file patterns\n\n```env\n# .env development\nAPP_ENV=development\nDB_HOST=localhost\nDB_PORT=5432\nNEXT_PUBLIC_API_URL=http://localhost:3000\n\n# .env staging\nAPP_ENV=staging\nDB_HOST=staging-db.example.com\nDB_PORT=5432\nNEXT_PUBLIC_API_URL=https://staging-api.example.com\n\n# .env production (not committed to git, or committed with restrictions)\nAPP_ENV=production\nDB_HOST=prod-db.example.com\nDB_PORT=5432\nNEXT_PUBLIC_API_URL=https://api.example.com\n```\n\n| Environment | `.env` file location | Committed to git? |
| :--- | :--- | :--- |
| **Development** | Yes, checked in. | Yes, safe (no real secrets). |
| **Staging** | Yes, checked in. | Yes, safe (no real secrets). |
| **Production** | Often not checked in. | No (or checked in with restrictions). |

### `NEXT_PUBLIC_` prefix in Next.js

```env\n# .env\nNEXT_PUBLIC_API_URL=https://api.example.com\nAPI_URL=https://internal-api.example.com\n```\n\n| Variable | Available in client bundle? | Available in server code? | Secret? |
| :--- | :--- | :--- | :--- |
| `NEXT_PUBLIC_API_URL` | Yes — embedded in the static HTML/JS. | No — not available on the server. | **No** — safe to commit to git. |
| `API_URL` | No — not embedded in the client bundle. | Yes — inlined into the server code at build time. | **No** — not a secret, but not in the client. |
| Real secrets (DB passwords, API keys) | No — do not use `NEXT_PUBLIC_` prefix. | No — pass at runtime with `-e` or a secrets manager. | **Yes** — never bake into the image. |

## 3. Command example\n\n### `.env` file and Compose variable interpolation\n\n```bash\n$ cat > .env\nAPP_ENV=development\nDB_HOST=db\nDB_PORT=5432\nNEXT_PUBLIC_APP_NAME=my-app\n```\n\n```yaml\n# compose.yaml\nservices:\n  api:\n    build: .\n    environment:\n      - APP_ENV\n      - DB_HOST\n      - \"DB_PASSWORD=${DB_PASSWORD}\"\n      - NEXT_PUBLIC_APP_NAME\n    env_file: .env\n```\n\n```console\n$ docker compose up -d\n```\n\n```console\n$ docker exec api env | grep -E 'APP_ENV|DB_HOST|DB_PASSWORD|NEXT_PUBLIC_APP_NAME'\n```\n\nOutput: `APP_ENV=development`, `DB_HOST=db`, `DB_PASSWORD=secret` (from the explicit `${DB_PASSWORD}` interpolation), `NEXT_PUBLIC_APP_NAME=my-app`.\n\n### `.env` file without interpolation (bare values)\n\n```env\n# .env\nAPP_ENV=development\nDB_HOST=db\n```\n\n```yaml\n# compose.yaml\nservices:\n  api:\n    environment:\n      - APP_ENV\n      - DB_HOST\n```\n\nCompose reads the `.env` file and makes those variables available. You reference them in the\nservice definition without `${}` — Compose handles the interpolation.\n\n### `-e` flag overrides `.env` file\n\n```console\n$ docker compose up -d\n```\n\n```console\n$ docker compose -e APP_ENV=production up\n```\n\nThe `-e APP_ENV=production` on the command line overrides `.env: APP_ENV=development`. The\nservice gets `APP_ENV=production`.\n\n### `.env` file with `env_file` in Compose\n\n```yaml\n# compose.yaml\nservices:\n  api:\n    image: myapp:1.0.0\n    env_file: .env\n```\n\nThe `.env` file in the project directory is automatically discovered by Compose. You do not\nneed to specify `env_file: .env` if the file is in the same directory as `compose.yaml`, but\nexplicitly adding it makes your intentions clear.\n\n### Different `.env` files for different environments\n\n```bash\n# Development\n$ cat > .env.dev\nAPP_ENV=development\nDB_HOST=localhost\n\n# Staging\n$ cat > .env.staging\nAPP_ENV=staging\nDB_HOST=staging-db.example.com\n\n# Production\n$ cat > .env.prod\nAPP_ENV=production\nDB_HOST=prod-db.example.com\n```\n\n```console\n# Development\n$ docker compose -f compose.yaml -f .env.dev up  # or just `docker compose up` if .env is in the dir\n\n# Staging\n$ docker compose -f compose.yaml -f .env.staging up\n\n# Production\n$ docker compose -f compose.yaml -f .env.prod up\n```\n\nOr, use the `COMPOSE_FILE` environment variable:\n\n```console\n$ COMPOSE_FILE=compose.yaml:.env.staging docker compose up\n```\n\n### Verify env vars inside the container\n\n```console\n$ docker compose exec api printenv | grep -E 'APP_ENV|DB_HOST'\n```\n

Output depends on which `.env` file is active and the precedence chain.\n\n## 4. When to use environment-specific config and when NOT to\n\n### Use environment-specific config when\n\n- **You build once and promote the same image** to staging and prod. The image is identical;\n  only the config changes.\n- **You have more than 3 environment variables.** Typing `-e` flags on the command line gets old fast.\n- **You want to commit `.env` files for dev and staging** (they contain no real secrets).\n- **You want variable interpolation.** `${VAR}` inside the Compose file is a clean way to reference\n  other variables.\n- **You are using `NEXT_PUBLIC_` variables** in Next.js and need them available at runtime.\n\n### Do not use environment-specific config when\n\n- **You have only 1-2 variables.** `-e` flags on the command line are simpler.\n- **You are using real secrets** (DB passwords, API keys). Use a secrets manager (Docker secrets,\n  HashiCorp Vault, GitHub Actions secrets) or `-e` at runtime, not `.env` files committed to git.\n- **You want `.env` committed to production.** Production `.env` files should not contain real secrets.\n  Either use a secrets manager or document that the `.env` file has had secrets removed.\n- **You expect `$VAR` in shell scripts to be Compose variables.** Compose uses `${VAR}` syntax.\n  `$VAR` in a Compose `.env` file may not be interpreted correctly, or may be interpreted as a\n  shell variable if your shell processes the file.\n\n### A practical environment-config pattern\n\n```env\n# .env (in the compose project directory, committed to git for dev/staging)\nAPP_ENV=development\nDB_HOST=db\nDB_PORT=5432\nNEXT_PUBLIC_APP_NAME=my-app\n```\n\n```yaml\n# compose.yaml — production base\nservices:\n  api:\n    build: .\n    environment:\n      - APP_ENV\n      - DB_HOST\n      - DB_PORT\n    env_file: .env\n    restart: unless-stopped\n    healthcheck:\n      test: [\"CMD\", \"node\", \"-e\", \"fetch('http://127.0.0.1:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))]\n      interval: 10s\n      timeout: 3s\n      start_period: 5s\n      retries: 3\n    deploy:\n      resources:\n        limits:\n          memory: 256M\n          cpus: '0.5'\n\n  db:\n    image: postgres:17-alpine\n    environment:\n      - POSTGRES_USER\n      - POSTGRES_PASSWORD\n      - POSTGRES_DB\n    env_file: .env\n    volumes:\n      - pgdata:/var/lib/postgresql/data\n    restart: unless-stopped\n    healthcheck:\n      test: [\"CMD\", \"pg_isready\", \"-U\", \"learn\", \"-d\", \"learndb\"]\n      interval: 10s\n      timeout: 3s\n      start_period: 5s\n      retries: 3\n\nnetworks:\n  appnet:\n    driver: bridge\n\nvolumes:\n  pgdata:\n```\n\n```yaml\n# compose.override.yaml — development overrides (git-ignored)\nservices:\n  api:\n    environment:\n      APP_ENV: development\n    command: [\"node\", \"--watch\", \"server.js\"]\n    volumes:\n      - .:/app\n      - node_modules_keep:/app/node_modules\n\nvolumes:\n  node_modules_keep:\n```\n\n```console\n# Development: dev settings from override + .env\n$ docker compose up\n# Production: base file only (no override), .env provides prod config\n$ docker compose -f compose.yaml up\n```\n\n## 5. Common mistakes\n\n**1. Using `$VAR` instead of `${VAR}` in `.env` files.**\n\nDocker Compose uses `${VAR}` syntax for variable interpolation. `$VAR` may not be interpreted\ncorrectly, or may be interpreted as a shell variable if your shell processes the file.\n\n**2. Committing production `.env` with real secrets to git.**\n\n`.env` files for production should not contain real secrets (DB passwords, API keys).\nEither use a secrets manager or remove them from the `.env` file and pass at runtime with `-e`.\n\n**3. Not understanding `.env` precedence.**\n\n```yaml\nservices:\n  api:\n    environment:\n      APP_ENV: production\n    env_file:\n      - .env\n```\n\nIf `.env` contains `APP_ENV=development`, the `env_file` overrides the inline `environment`\n(because `env_file` has higher precedence than inline `environment`). The service gets\n`APP_ENV=development`. Know the precedence chain.\n\n**4. Using `.env` for real secrets and wondering why they are exposed.**\n\nIf `.env` contains `DB_PASSWORD=secret` and is committed to git, the secret is in git.\n`.env` files are typically checked into dev/staging repos but should never be committed to\nproduction repos if they contain real secrets.\n\n**5. `$VAR` in a Compose command string being a Compose variable, not a shell variable.**\n\n```yaml\ncommand: [\"sh\", \"-c\", \"echo $MY_VAR\"]\n```\n\nIf `MY_VAR` is set in `.env`, Compose will replace `$MY_VAR` with the `.env` value (or empty\nif not set), not the shell variable. To pass a shell variable, escape it as `$$MY_VAR` or use\n`-e MY_VAR=$MY_VAR` on the command line.\n\n**6. Forgetting that `.env` interpolation happens at Compose load time, not runtime.**\n\nThe `.env` file variables are substituted when `docker compose up` runs, not when the container\nstarts. If you need a variable at runtime inside the container, it must be baked in with `ENV` in\nthe Dockerfile or passed with `-e` at `docker run` time.\n\n**7. Using the same `.env` file for dev and production with real secrets.**\n\nDev `.env` may have `DB_PASSWORD=dev-secret`, but production should not have any real\nsecrets in `.env`. Use a secrets manager or `-e` flags for production.\n\n**8. `.env` file with `=` in the value, not quoted.**\n\n```env\n# Bad: value contains an unquoted equals sign\nDB_CONNECTION=postgresql://user:pass@host:5432/db\n```\n\nDocker Compose may split at the first `=`. Write: `DB_CONNECTION="postgresql://user:pass@host:5432/db"`\nor use `DB_CONNECTION=postgresql://user:pass@host:5432/db` with careful parsing.\n\n**9. Not using `export` to make `.env` variables available in the shell.**\n\nCompose `.env` variables are only available to Compose, not to the host shell. To use them in\na shell script, `source .env` or use `docker compose env`.\n\n**10. `.env` file with BOM (Byte Order Mark).**\n\nSome editors (Windows Notepad) add a BOM to `.env` files, which can cause Compose to fail\nwith a parsing error. Use a text editor that does not add BOM (VS Code, Vim, Emacs, etc.).\n\n---\n
